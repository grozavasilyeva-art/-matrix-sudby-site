# ЮKassa: подготовка безопасного создания платежа

**Статус:** локальный серверный код и офлайн-тесты. Настоящие платежи не включены, API-ключи не подключены, публичного маршрута покупки нет.

## Что реализовано в develop

- `server/yookassa-checkout.mjs`: создание платежа по официальному серверному API ЮKassa, сумма строго **550.00 RUB**, `capture: true`, `confirmation.type: redirect`, `metadata.order_id`.
- `server/sqlite-checkout-intents.mjs`: хранит отдельный ключ идемпотентности для каждого заказа **до первого обращения к платёжному API**. После ответа сохраняет ID платежа и адрес страницы оплаты. Повторный запрос использует исходный ключ.
- `server/yookassa-verifier.mjs` и `server/fulfillment.mjs`: уже подготовленная проверка состояния платежа отдельным GET-запросом перед выпуском отчёта.
- `scripts/yookassa-checkout.test.mjs` и `scripts/sqlite-checkout-intents.test.mjs`: только фиктивные сетевые ответы, никакого доступа к ЮKassa.

## Важный алгоритм для будущего боевого сервера

1. Сервер получает только данные, необходимые для заказа. Он проверяет дату рождения и назначает **550 ₽ самостоятельно**.
2. Создаёт черновик заказа в доверенной БД и фиксирует стабильный уникальный ID.
3. **До запроса в ЮKassa** сохраняет ключ идемпотентности для этого заказа в транзакционной БД.
4. Вызывает `createYooKassaCheckout(...).createPayment(trustedDraft, persistedKey)`.
5. Сохраняет платежный ID, привязку к заказу и защищённую ссылку подтверждения; транзакционно переводит заказ в ожидание оплаты. В случае сбоя повторяет **то же действие с тем же ключом**, а не генерирует новый.
6. Возвращает клиенту только адрес страницы оплаты (HTTPS), никогда секрет API.
7. Получив webhook `payment.succeeded`, **независимо** повторно запрашивает платёж у ЮKassa, сверяет ID заказа, ID платежа, валюту, сумму и успешный статус.
8. Только после подтверждённого платежа закрытый исполнитель генерирует полный персональный PDF.
9. При отмене, возврате и недоступности платёжного сервиса повторно анализирует состояние заказа, а не угадывает исход по возвращению покупателя на сайт.

## Что НЕ сделано и почему нельзя включать оплату

- Не создан публичный HTTPS checkout endpoint с полноценной авторизацией и контролем доступа.
- Новый checkout использует транзакционную привязку платежа в SQLite. Фоновая сверка зависших платежей и производственная очередь ещё отсутствуют.
- Не реализованы боевые webhook, возвраты, чек (54-ФЗ в применимом сценарии), резервное копирование, защита от массовых заявок на периметре.
- Не выбран российский хостинг для хранения персональных данных, нет работающего производственного мониторинга затрат.
- Сам отчёт всё ещё требует редакционного утверждения перед продажами.

Никогда не размещать токены, персональные данные, полную платную библиотеку или переменные `SHOP_ID`, `SECRET_KEY` в публичном JavaScript либо репозитории.

**Принцип проекта:** бесплатный калькулятор работает локально в браузере; сервер и эквайринг используются только для платных заказов. При разработке и выполнении офлайн-тестов облачные лимиты не расходуются.

## Объединённый checkout и уведомления (24.11.2026)

- В `server/sqlite-orders.mjs` таблица checkout_drafts теперь хранит черновик, хеш токена доступа и ключ идемпотентности до сетевого вызова. Привязка платежа и запись заказа выполняются в одной транзакции SQLite.
- `server/checkout-service.mjs`: создаёт серверный ID, выдаёт индивидуальный токен доступа, проверяет токен перед созданием платежа, повторно использует сохранённый ключ. Автоматические повторы прекращаются через 23 часа от записи черновика или при изменении конфигурации магазина; требуется ручная сверка. ЮKassa гарантирует идемпотентность только 24 часа после первого запроса.
- `server/payment-notifications.mjs`: внутренний обработчик события payment.succeeded. Не доверяет статусу из тела уведомления; известный платёж передаётся модулю fulfillment для независимой проверки через API. Неизвестный ID не запускает запрос к провайдеру или PDF. Ответ 200 только после завершения обработки либо для уже завершённого заказа; при временной ошибке предусмотрен повтор.
- `scripts/checkout-service.test.mjs`: офлайн-проверки сбоя сети, восстановления ключа после перезапуска, срока повторов, смены конфигурации, токена доступа и ложного/повторного уведомления.

**Не развёрнуто и не готово к продажам:** публичный HTTPS-маршрут, настоящий тестовый магазин ЮKassa, проверка источника webhook и ограничения трафика на периметре, долговечная очередь и сверка зависших платежей, обработка отмен и возвратов. При ответе 503 провайдер повторяет доставку ограниченное время; для оплаченных заказов обязательна отдельная сверка. До запуска также нужны неизменяемые ключи файлов для каждого поколения отчёта (чтобы просроченный исполнитель не перезаписал готовый PDF), резервное копирование, правовые условия и мониторинг затрат. Старый отдельный адаптер checkout_intents сохранён для регрессионных тестов, но новый checkout использует единую SQLite-базу.
