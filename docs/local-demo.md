# Локальный тестовый сервер «Матрицы судьбы»

## Назначение

Проверка полного технического пути: **заявка → фиктивная оплата → проверка прав → генерация PDF → скачивание** без списаний, аккаунтов, банковских ключей и облачных вызовов.

**НЕ ДЕПЛОИТЬ В ИНТЕРНЕТ.** Это демонстратор с транзакционной SQLite-базой на одном локальном компьютере. Он не заменяет HTTPS, производственную БД и резервное копирование, действующую банковскую интеграцию, резервирование и защиту от ботов. При запуске сервер слушает только `127.0.0.1` на случайном порту; при `NODE_ENV=production` запуск запрещён.

## Запуск на компьютере

Требуется Node.js 22+. Из корня репозитория:

```sh
node --test scripts/*.test.mjs
node dev/start-local.mjs
```

По умолчанию генератор отдаёт **одностраничный технический PDF с надписью LOCAL TEST ONLY**. Это не продаваемый отчёт и не платная библиотека.

Для полноценного отчёта V3 локально распакуй свой **приватный** архив *за пределами публичного репозитория*. Установи Python и нужные библиотеки (из инструкции приватного архива). Затем укажи `PRIVATE_PDF_DIR` как абсолютный путь к каталогу с `generate_luxury_report.py`, например:

```sh
PRIVATE_PDF_DIR=/private/path/report-v3 node dev/start-local.mjs
```

Нельзя коммитить этот архив, готовые платные PDF и приватные шрифты в публичный GitHub.

## Проверка API

Старт выведет адрес `http://127.0.0.1:ПОРТ`. Далее использовать указанный порт.

```sh
# Проверить локальный сервер
curl http://127.0.0.1:ПОРТ/health

# Создать заявку. Цена всегда 550 ₽, из серверного кода.
curl -X POST http://127.0.0.1:ПОРТ/api/orders \
 -H 'Content-Type: application/json' \
 -d '{"birthDate":"1989-08-23"}'
```

В ответе будут **orderId** и **accessToken**. Токен сохраняется в клиенте только на время локального теста, в файле данных хранится его SHA-256. Не выкладывать реальные токены или даты покупателей в логи и скриншоты.

```sh
# Получить состояние заказа
curl http://127.0.0.1:ПОРТ/api/orders/ORDER_ID \
 -H 'Authorization: Bearer ACCESS_TOKEN'

# ИСКЛЮЧИТЕЛЬНО ЛОКАЛЬНО: подтвердить поддельную оплату
curl -X POST http://127.0.0.1:ПОРТ/api/dev/orders/ORDER_ID/confirm \
 -H 'Content-Type: application/json' \
 -H 'Authorization: Bearer ACCESS_TOKEN' \
 -H 'X-Local-Demo: acknowledge-fake-payment' \
 -d '{}'

# Скачать тестовый PDF
curl http://127.0.0.1:ПОРТ/api/orders/ORDER_ID/report \
 -H 'Authorization: Bearer ACCESS_TOKEN' \
 -o matrix-test.pdf
```

Попытки получить документ без токена или до подтверждения фиктивной оплаты отклоняются. Заказы сохраняются в локальной SQLite-базе `.matrix-demo-data/orders.sqlite`, а PDF в приватном каталоге `.matrix-demo-data/reports/`. Оба сохраняются между перезапусками. Эти данные нельзя использовать как производственное хранилище. Папка исключена из Git.

## Тесты в GitHub

`scripts/local-demo.test.mjs` запускает сервер только на `127.0.0.1`, создаёт фиктивную заявку, убеждается в отсутствии доступа до оплаты, имитирует оплату, скачивает PDF, повторяет подтверждение и проверяет восстановление после перезапуска. Банк, Netlify и Yandex Cloud не вызываются.


## Ограничение запросов в локальной версии

- `POST /api/orders` ограничен **30 запросами в минуту с одного локального IP**. При превышении сервер возвращает HTTP `429 Too Many Requests` и заголовок `Retry-After`.
- `GET /health`, просмотр своего заказа и скачивание оплаченного **тестового** отчёта остаются доступны при превышении лимита создания новых заявок.
- Приватный Python-генератор обрабатывает **один отчёт одновременно**, максимум **четыре ожидающих**. Если очередь заполнена, лишний запрос отклоняется и его потребуется повторить. Это НЕ готовая долговечная очередь оплаченных заказов.
- Запросы распознаются по `req.socket.remoteAddress` в локальной сети процесса, **не по ненадёжному заголовку X-Forwarded-For**.
- Оба механизма работают в оперативной памяти процесса, не распределены между серверами, не являются полноценной антибот-защитой и не исключают вызовы из облачного биллинга.
- **Нельзя публиковать тестовый `/api/dev/.../confirm` в интернет.** Он предназначен исключительно для фальшивой оплаты на локальном компьютере.

## Что предстоит до продаж

1. Реальная транзакционная БД заказов с атомарными заявками/очередью, политикой удаления и резервированием.
2. Закрытый HTTP API с HTTPS, полноценной авторизацией, подтверждением ЮKassa отдельным запросом по ID и защитой от мошеннических вебхуков.
3. Ограничение частоты и антибот до расходов на PDF; алерты по нагрузке и стоимости.
4. Приватное хранилище и короткоживущие ссылки; обработка возвратов, ошибок, повторных доставок.
5. Проверка юридических условий, чеков и качества полного платного PDF.
6. Только потом можно отдельно согласовать включение реальных платежей.

Ветка `develop` остаётся тестовой, ветку `main` и работающий сайт эта демонстрация не затрагивает.


## Проверка настоящего приватного PDF V3

Чтобы пройти весь сценарий с закрытым генератором (не с одностраничной заглушкой), установи Python, ReportLab, Poppler и распакуй приватный архив ВНЕ публичного GitHub. Затем запусти:

```sh
PRIVATE_PDF_DIR=/absolute/path/to/private-v3 node --test scripts/private-e2e.test.mjs
```

Тест имитирует заказ и оплату, скачивает итоговый файл, проверяет PDF-сигнатуру, 31 страницу через pdfinfo и дату 29.02.2000 через pdftotext. Если переменная не задана, тест пропускается в публичном CI, а библиотека платных текстов никуда не загружается.

## SQLite и будущий хостинг

Сейчас заказ хранится в локальной SQLite с атомарным захватом задания и защитой от повторной генерации. В Node 22 модуль node:sqlite имеет статус experimental, поэтому перед выбором постоянного хостинга нужно закрепить поддерживаемую версию Node и проверить миграции/резервное копирование.

Это ещё НЕ распределённая база для нескольких серверов, не автоматический балансировщик и не защита от сбоя площадки. При выборе serverless-хостинга потребуется совместимая постоянная транзакционная БД.
